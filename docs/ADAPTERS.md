# Output adapter contract

Studio owns `DisplayLayouts`, its versioned Store, background images, selected HA data caches, editor/admin endpoints and generic browser assets. Each config entry owns exactly one layout library and one output adapter. Layout subscriptions and caches are closed by Studio, not by the hardware integration.

`providers.py` defines the initial adapters with this common interface:

- `kind`, `status` (connection and explicit `hdmi`, `pip`, `overlay`, `startup`, `screenshot` capabilities), `selected_view`.
- `async_start()`, `async_show_view(view, transition, duration, theme)`, `async_notify(title, message, layout, duration)`, `async_close()`.
- Browser transport uses a scoped token, bounded 25-second long polling and immediate wake-up for selected entity/layout/view changes. One display-renderer clock ticks locally once per second. Camera/cover work is cached and tied to visible widgets. Unsupported hardware views fail explicitly.

The LG adapter imports only `custom_components.lg_rs232_ip.api.get_display_api(..., version=1)`. It requires `studio_api_version >= 1`, added in LG 2.32.0. That extension exposes:

- `studio_status` for capability/connection/cache confirmation.
- `async_bind_studio(owner, layouts, assets, version)` and `async_unbind_studio(owner)` with owner checks.
- `async_show_studio_view(...)`; native notification transport uses the existing `async_present("show_display_app", ...)` API.

LG serves bound generic assets through its existing paired app URL and reports `studio_version`; the native app reloads once when the renderer is attached, upgraded or detached. The editor and storage are never imported by LG. Without Studio, hardware entities, remote, native presentation, basic app notifications and resident HDMI remain available. Studio sources disappear until the extension is connected again. Existing AV API version 1 remains unchanged.

The adapter listens to LG's public `lg_rs232_ip_status` event and rebinds after LG reload. Rebinding is serialized and idempotent; a different Studio owner is rejected. Studio unload releases only its binding, not SI installation or hardware settings. LG unload leaves the independent layout store alive. The legacy-import module is the sole compatibility reader of old LG layout storage; it never edits or deletes it.

A new native display adapter should implement this provider contract and add a config-flow choice. Hardware drivers should expose a versioned API comparable to LG's, without importing Studio internals or assuming other hardware's capabilities. Keep power, native source selection and recovery inside the device integration. A browser-capable display can already use the generic provider without writing an adapter; native boot, capture or HDMI PiP are not inferred from browser support.

The ESPHome provider imports only `custom_components.esphome_display.api.get_display_api(..., version=2)`. It shares BrowserProvider's views, messages, configured touch actions and expiry/return timers. The native binding supplies the production scene compiler, selected-resource callback and common action executor through `async_bind_native`. Studio owns the editor and layout model; the hardware bridge never imports Studio internals. Protocol 2/schema 3 describes native LVGL widgets and separately selected RGB565 assets. A local board-camera widget contains no HA resource URL.

The native engine and JPEG decoder are compiled unchanged in firmware and real LVGL host tests. Canonical background and solar palettes live in the browser runtime and are consumed by the native compiler, preventing independent colour tables. HA pushes complete revisions through the standard ESPHome `studio_push_scene` action; the configured node name restricts the target. Only a matching physical acknowledgement confirms display and connectivity. Native API failure falls back to scoped HTTP. Stale scenes/actions and repeated input sequences are rejected; a touch reply includes the current scene. A server push alone never claims device connectivity.

The HTTP browser kiosk uses the original Studio runtime, long polling and the same configured action executor. Renderer/JPEG compatibility remains available for an explicit legacy bridge. Browser, LG and ESP are exercised against the same layout library and runtime sources; pinned/latest-upstream CI, three firmware builds and native host tests detect drift. ESP layouts migrate HDMI placeholders to local-camera widgets and hide the HDMI-only view; dashboard PiP and PiP notifications use a single local camera. Unsupported HLS sources remain explicit placeholders. The HTTP kiosk and LG keep their own capabilities.

Optional LG load ordering uses Home Assistant's [after_dependencies](https://developers.home-assistant.io/docs/creating_integration_manifest/#after-dependencies); LG is not a required dependency. The Studio browser test suite runs without the LG package in its import path. LG's separate suite tests the combined native app/renderer contract.

The ESP startup widget shares checked defaults and part geometry with the firmware. Only a saved offline startup bundle is attached to ordinary native scenes; live drafts use the saved base library for this bundle. Firmware validates its size/content, writes it to NVS only when the version changes, and acknowledges the saved version. The editor reports success only for the matching version from a connected physical display. Until time sync, cached clock/date text is blanked instead of presenting stale time.

ESP adapter API 2 optionally exposes `status.camera_preview` with `stream_entity_id` and `snapshot_entity_id`. The bridge resolves these from the selected native ESPHome config entry and entity registry (including renamed/disabled entities); no device URL or credentials cross this boundary. Studio forwards the descriptor in its admin catalog and editor documents. Old adapters without this optional descriptor remain supported. The admin-only `camera_preview.js` requests HA's authenticated `camera/stream` WebSocket HLS URL, uses native HLS or the locally vendored hls.js build, and falls back to authenticated `camera_proxy` stills. It never changes the saved `camera_source: local`, the native scene, or the kiosk/LG transport. The shared ES5 layout renderer accepts an optional preview factory; no HLS library is shipped to the ESP or LG. Geometry/fit changes reuse the decoder; modal previews, hidden tabs, removed parts and navigation release it. Joint contract and Chromium/WebKit tests cover mapping, lifecycle, crop, fallback and unchanged saved/native layouts. `tools/camera_preview_acceptance.py` verifies actual decoded frames against HA and the physical ESP.
